## Decisions

- **Load order is parse → migrate → validate, not parse → validate → migrate.** The card lists validate before migrate, but a v1 record can't pass the v2 validator before it is migrated. `migrateProfile` checks the envelope (an object with an integer `schemaVersion` ≤ current) before it runs any step, and the full validator runs on the result. A record whose `id` differs from its key also counts as corrupt.
- **Records are JSON strings**, not structured-clone objects: `put(JSON.stringify(p), id)`. Load then really is "parse", the memory store returns copies, and a damaged record can't be half-readable.
- **A damaged current is never copied over prev.** On save, current is copied to `<id>:prev` only if it reads as a good profile itself; otherwise the old prev stays. Without this, one save after a corrupt write would destroy the last good snapshot.
- **One transaction per save:** list the keys (profile limit) → read current and prev → refuse a newer one → check current → put prev → put current, all in one `readwrite` transaction. If any step throws, the transaction is aborted and nothing is written. The memory backend does the same work synchronously.
- **A save from a newer build is never overwritten (review item 1).** Only `schemaVersion` is read to decide this, because a newer build may have changed every other field. If the stored current or prev is newer, `save` rejects with `NewerSaveError` and writes nothing. If current is newer, `load` returns null with no fallback to the older prev, so an old tab or a stale cached build can't show rolled-back progress and then save it. A newer prev with a good current still loads current.
- **`save` validates first, then compacts (review item 3), then writes.** It rejects (throws) an invalid profile, a `schemaVersion` other than the current one, an id with `:`, a 9th profile (`ProfileLimitError`), a newer stored record (`NewerSaveError`) and a storage failure. A bad write must never replace good data.
- **`load` and `listProfiles` never reject (review item 2).** A storage failure is reported as `storageError` and gives `null` / `[]`. `importAll` never rejects either. `exportAll` and `remove` still reject on a storage failure, so an export never silently leaves a profile out.
- **A closed IndexedDB connection is retried once.** `blocking()` can close the connection under a call that is in flight. Every backend call then reopens and tries once more on `InvalidStateError`. `transaction()` throws before anything is written, so the retry can't write twice. This path is not covered by a unit test, because fake-indexeddb can't easily close a connection mid-call.
- **Compaction runs inside `save`**, so a stored profile never has more than 500 history entries. Week rows use the local Monday. Averages are weighted by session count, and two rows for the same week merge, so no minutes are lost.
- **Problems go to `onProblem` and to `console.warn("[save] …")`** (review item 5, approved). Kinds: `restoredPrev`, `unreadable`, `newerVersion`, `storageError`. I added `message` (for logs) to the suggested shape, and made `profileId` `string | null`, because a failed listing is not about one profile. A callback that throws is caught. Nothing is sent anywhere. `createMemoryStore` takes the same options, which is also additive.
- **Id collision on import:** the copy gets `newId()` and `"<name> (2)"`, or `(3)` … if that name is taken too, cut to fit 16 chars. Two profiles with one id in the same file both arrive. Profiles whose ids contain `:` are re-id'd the same way.
- **The profile limit counts every stored profile id**, including one whose records are both damaged or newer. `save` and `importAll` count the same way (review item 6: behavior unchanged).
- **Import error strings are short English sentences for a grown-up** (`"The file is bigger than 5 MB."`, `"Profile 2: profile.name: missing"`). They are not kid-facing, and they are not run through `t()`, because `SaveStore` returns `string[]`. The Settings UI may map them.
- **Default font is `pixel` for every band** (PLAN.md §4.6 calls pixel the default). Other shared defaults: `reducedMotion: 'system'`, volumes master 0.8 / music 0.5 / sfx 0.8 / voice 1, `quality: 'auto'`, `breakReminderMin: 15`, `layout: 'en-US'`. Miner text scale 1.25, Builder 1.0.
- **Validator limits:** extra keys are allowed (forward-tolerant); numbers must be finite; name length is counted in code points (1–16) and a name can't be blank or only whitespace; dates must be real calendar dates (`2026-13-45` and `2026-02-29` fail); accuracy-like fields must be 0–1; counts must be whole numbers ≥ 0; `unlockedBiomes` has no duplicates. Records keyed by user data (`keyStats`, `bigramStats`, `inventory`, `achievements`, `progress.lessons`) refuse the keys `__proto__`, `constructor` and `prototype`. `keyStats` keys must be 1 char and `bigramStats` keys 2 chars. The game-mode list is a `Record<GameModeId, true>`, so typecheck fails if `GameModeId` changes. The nickname blocklist is not checked here (M1-10's validator is build-time only).

## Notes for downstream tasks

- **APIs beyond the contract** (all additive): `SCHEMA_VERSION`, `NAME_MAX`, `profileProblem`, `isProfile` (schema); `migrateProfile` (migrations); `uuidFromBytes` (id); `compactHistory`, `localWeekStart`, `HISTORY_CAP` (compact); `createStoreOn`, `Backend`, `createMemoryBackend`, `ProfileLimitError`, `suffixedName`, `MAX_PROFILES`, `MAX_IMPORT_BYTES`, `EXPORT_APP`, `DEFAULT_DB_NAME`, `PROFILES_STORE` (store).
- IndexedDB layout: database `voxel-typer` (version 1), object store `profiles` with out-of-line keys, `<id>` and `<id>:prev`, values are JSON text.
- Profile-creation UI: check the nickname against the blocklist yourself; `save` only checks length.
- To bump the schema: raise `SCHEMA_VERSION`, add `migrations[old]`, add `tests/fixtures/saves/v<N>.json`, and update the validator. `migrations.test.ts` already checks one step per version.
- The e2e fixtures are raw `Profile` objects. Seed them with `store.save(p)`, or wrap them as `{ app: 'voxel-typer', version: 1, profiles: [p] }` for the import UI.
- `createIdbStore` opens the database lazily. On `blocking` (another tab upgrading) it closes its connection, then reopens on the next call, or retries once on a call that was in flight.
- **Damaged profiles still take a slot (M3-12).** A profile whose records are both damaged is hidden from `listProfiles` but still uses one of the 8 slots. `listProfiles` (and `load`) report it through `onProblem` with `kind: 'unreadable'` and its `profileId`. Use that to offer a grown-up "remove this damaged profile" behind the parent gate; `remove(profileId)` deletes it. A profile saved by a newer build shows up the same way as `newerVersion`. Say "update the game" there, not "delete".
- **Autosave must catch a rejected `save`.** It rejects on an invalid profile (a NaN from a stats bug, say), a 9th profile, a newer stored record or a storage failure. Keep the session going and show a calm message; don't crash, and don't retry in a loop. `NewerSaveError` and `ProfileLimitError` are their own classes.
- `onProblem` wording for kids and families goes through `t()` in the UI. `restoredPrev` might read "We brought back your last save". The `message` field is English, for logs only.
