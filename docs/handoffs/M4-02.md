## Decisions

- **Scrubber approach: drive `update(dt)`, no new runtime API.** Pausing (or touching the scrubber) takes the model off the driver. A scrub to `t` calls `play(anim, { restart: true, fadeMs: 0 })` and then `update(t)`. Play adds it back to the driver from that time. The scrubber's own readout is a loop system that mirrors the anim time; it never asks for frames. So when the anim is paused the loop idles (an e2e test checks this).
- **Shader problems are e2e failures (M4-01 re-review m31).** The spec fails on any console error, any page error, and any console warning that looks like a three.js or WebGL message (`THREE.`, `WebGL`, `shader`, `GL_`, `program`), except Chrome's "GPU stall" performance note. three reports a failed compile or link with `console.error` and a non-empty program log with `console.warn`. **Proved by mutation:** I changed `vMapUv` → `vUv` in the shader patch. The "opens every model" test then failed with `THREE.WebGLProgram: Shader Error … VALIDATE_STATUS false`. I put the patch back.
- **Pooled mob grows in after `defeat` (M4-01 re-review): fixed here, since it was small.** Showing an instance now ends any crossfade (`Animator.snap()`). A `play` on a just-shown instance, before its next `update`, doesn't fade. Both orders, "play then show" and "show then play" in the same frame, appear at full size on the first frame. A `play` after that still crossfades as before. The tests fail without the fix.
- **m25** was already handled in the code (`safeSpeed` on the replay path); only the test was missing. The new tests cover `0`, `-1`, `NaN` and `±Infinity` given when replaying the running one-shot (it jumps to the end and fires `onEnd` once) and the running loop (it holds its first frame, with no NaN pose). Another test checks that a good speed afterwards plays again.
