## What changed

- `src/render/atlas/build.ts`: `buildAtlas` (contract) is built from pure helpers: `planTiles`, `packAtlas`, `createAtlasLookup`, `tileRect`, `tileUv` and `atlasSize`. It also applies PNG overrides through `import.meta.glob('/assets/textures/src/*.png')` and adds `paintCrackStages(seed)` and `buildCrackTextures(seed)`.
- `assets/textures/src/README.md`: override naming, size and originality rules.
- `atlas.html` + `src/dev/atlas-preview.ts`: developer page. It shows every tile at 8× with the block and faces that use it, the 10 crack stages, the packed atlas at 2×, the palette ramps and each biome's shifted ramps. Parameters: `?seed=<n>` (default 1) and `?biome=<id>` (default meadow).
- `tests/unit/atlas/{painters,palettes,build}.test.ts`: 92 tests.
- `tests/e2e/atlas.spec.ts`: loads `/atlas.html?seed=1` and checks for no console errors, one card per tile plus the crack stages, and hard-edged 8× tiles. Then it takes a full-page `toHaveScreenshot("atlas.png")`.

## Decisions

- **`vite.config.ts` changed (outside Owns, the smallest change that works).** e2e runs against the `--mode test` build, so `atlas.html` must be in `dist-test/` and not in `dist/`. `build.rolldownOptions.input` lists `index.html`, and adds `atlas.html` only in test mode. `vite dev` serves it anyway. Checked: `dist/` has no `atlas.html`. One side effect in the test build only: three.js now goes into a shared chunk.
- **`PaletteRampId` is a union, generated from the runtime `PALETTE_RAMP_IDS` array.** M2-04's registry test can then check a recipe's ramps at runtime. `Palette` keeps M1-01's provisional shape (hex strings, dark to light), so `src/content/blocks/types.ts` and the other users need no change.
- **Biome variants shift ramps, not the whole palette.** Each biome lists the ramps it changes, using tint (a mix toward a color), hue, saturation and lightness. A tint is needed because the stone ramps are nearly grey, and a hue shift alone barely changes a grey. Wool, ore, crystal-light and spark ramps stay the same in every biome, so a red block is red everywhere. A test checks this. Another test checks that every ramp in every biome stays dark to light by WCAG luminance.
- **Tile 0 is a magenta "missing" tile.** Unknown block nums and faces map to it, so a missing recipe shows up instead of quietly borrowing another tile.
- **Tile seeding:** `createRng(seed).fork('tile:<blockId>:<face>')` for each tile. Faces of one block with identical recipes share one tile. PNG overrides always get their own tile.
- **UV convention:** the texture keeps `flipY = true`, and UVs are inset by 1/64 texel. `v0` is the tile's bottom row and `v1` its top row, so on M1-13's side faces (v runs upward) the grass overhang is at the top.
- **Atlas layout:** a square 2^n atlas, at least 32 px, with 18-px cells in a grid. 50 tiles need 256 px, and 49 fit in 128.
- **Cracks aren't in the block atlas.** `buildCrackTextures(seed)` returns 10 separate 16×16 `CanvasTexture`s for the overlay material. All stages come from `createRng(seed).fork('crack')`, so each stage adds to the one before (a test checks that no pixel's alpha drops).
- **PNG overrides are decoded with `Image`.** `fetch` can't read the inlined data URIs under the CSP (`connect-src 'self'`). A file that isn't 16×16 or doesn't decode is skipped with `console.warn`.
- **The preview shows `SAMPLE_BLOCKS`** (42 sample blocks, one or more of each recipe kind and custom painter) while the block registry is empty. Once M2-04 adds blocks, it shows the real registry instead. That changes the baseline on purpose.
- **Originality choices:** wool is a knitted chevron pattern, not noise. Ores are small shaped clusters with a glint pixel and a cast shadow. Planks have nail heads at staggered end joints. Logs have off-center rings. The lamp block has a cross frame and four glowing panes. Pebble beds stand in for cobblestone. Every color was picked for this project, and no texture was traced from or modeled on another game.

## Notes for downstream tasks

- **M2-04 (blocks):** recipe ramps must be `PaletteRampId`s, and custom painters are listed in `CUSTOM_PAINTERS` (painters.ts doc comment). Some painters read a second ramp: `rings:<wood>` also reads `<wood>-bark`, `cap:<ramp>` reads `mushroom-stem` for spots, and `lamp:<ramp>` reads `metal`. Tag see-through blocks (`glass`, `ripple:water`) `'transparent'`; `atlas.transparent(num)` reads that tag. `src/dev/atlas-preview.ts` `SAMPLE_BLOCKS` has a working recipe for every kind to copy from. Your blocks replace the samples in the preview, so regenerate the `atlas.png` baseline with `/update-snapshots`.
- **M2-01 (render core):** `buildAtlas(blocks, paletteFor(biome), seed)` gives a ready `CanvasTexture` (Nearest, no mipmaps, sRGB). A biome change means rebuilding the atlas with the new palette, which is cheap (about 50 tiles). `buildCrackTextures(seed)` gives the Mine-mode crack layers.
- **M2-07 (UI kit):** `paletteFor(biome)` and `BASE_PALETTE` hold hex strings that CSS can use directly, and `paintTile` gives 16×16 RGBA for procedural 9-slice data URIs.
- `palettes.ts` is pure by construction but not in the `.oxlintrc.json` pure-zone list. The orchestrator may add it (one line) if pure code needs runtime palette data.
- Changing any painter, palette or sample block changes the three pinned hashes and/or the `atlas.png` baseline. Update both deliberately.
- The preview logs a Chrome `willReadFrequently` warning (not an error) because it reads the atlas canvas back once per tile. This is harmless.
