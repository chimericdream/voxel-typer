## What changed

- `src/ui/components/ImportExport.tsx` + `.module.css` (new): the Save file section.
  - **Export:** "Download a save file". It calls `store.exportAll()` and downloads `voxel-typer-<YYYY-MM-DD>.json`. The local date comes from the shell's `realClock.epoch()`; tests inject `now`. The download is a local object URL, so nothing goes over the network. Afterwards the screen says how many players were saved, and how many damaged or newer-game players were left out (see Decisions).
  - **Import:** "Load a save file" opens a file picker (`.json`). It reads the file with the new `readExportFile`, which never reads a file over 5 MB. Then it shows a **check before loading**: one row per player in the file, saying what will happen. Nothing is written until the grown-up presses **Load players**. Afterwards a summary: "Added N, updated N, not loaded N", with one line per player saying why.

  - `importAll` now uses `readExportFile`, so the file rules live in one place. Its behaviour and English strings are unchanged, with one exception: a Blob whose `text()` rejects now gives "The file could not be read." without the error text appended. The `SaveStore` interface is unchanged.

- `src/ui/screens/Splash.tsx`: one small button, "Grown-ups: load a save file", next to Privacy. On a new device the splash goes straight to "new player", so without this a family moving devices would have to make a throwaway player before they could import.

## Conflict rules (the grown-up decides; the default never overwrites)

For each player in the file:

| On this device                              | Row                                           | Choices (first = default)                                                      |
| ------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------ |
| no player with that id                      | **add**                                       | — (uses a free slot)                                                           |
| a readable player, same id                  | **conflict**                                  | Keep this device's · Use the file's copy · Keep both                           |
| a damaged ("lost") record, same id          | **conflict**                                  | Keep this device's · Use the file's copy (repairs it) · Keep both              |
| a newer game's record, same id              | **conflict**                                  | Keep this device's · Keep both (replace not offered; the store refuses it too) |
| the same id appears again later in the file | **add** as a copy (new id, `Name (2)`)        | —                                                                              |
| entry is damaged / from a newer game        | **bad**, listed with "Player N in the file …" | —                                                                              |

- Under each conflict:
  - Both copies are described: lessons done and last played, with "(newer)" on the copy played more recently.
  - A sentence spells out who wins, e.g. "The file's copy of Juniper replaces the one on this device." or "Juniper on this device stays as it is. The file's copy isn't loaded."
- **Keep both** gives the file's copy a fresh id and `suffixedName` (`Juniper (2)`), like `importAll`.
- **The cap of 8** (M3-09): every stored id counts, including damaged and newer-game ones.
  - New players and "keep both" copies fill the free slots in file order. The rest show "won't fit" in the check and "wasn't loaded: a device holds 8 players. Delete a player to make room…" in the summary.
  - Replacements don't need a slot.
  - `store.save` enforces the cap again (`ProfileLimitError` → reported as full).
- **Damaged slots:** a damaged record with the same id can be repaired by "Use the file's copy". Other damaged slots are still removed on Players (M3-09), or with the Settings "Go to Players" link, which reuses `app.removeProfile`.

## Data-loss review: every path, and its guard

1. **The file overwrites a player on this device.**
   - Only when a grown-up picked "Use the file's copy" for that row, after passing the parent gate. The default is "Keep this device's".
   - **A replace is final.** `store.save` moves this device's copy to `<id>:prev`, but that is not an undo: the next lesson, settings change or import drops it, and the game has no way to bring it back. So (review N2):
     - the wording says it plainly: "The file's copy of {name} replaces the one on this device. {name}'s progress on this device can't be brought back after that.";
     - whenever a readable player would be replaced, the check offers **"Download a save file first"** (the same export) above Load players, with "Replacing a player can't be undone…". It shows even where the export section is hidden (a new device), and the check stays open after the download;
     - repairing a damaged slot has nothing to back up, so no offer there.
   - Tests: "a replace offers a backup download first …" (the backup holds the device copy from before the import), "repairing a damaged slot has nothing to back up", and the e2e's second import.
2. **The file overwrites a newer game's save.** Not offered in the UI, and `store.save` throws `NewerSaveError` and writes nothing (M1-09). If it ever happens, the summary says "a newer version of the game saved this device's copy".
3. **A bad island in the file wipes a good island.**
   - `planImport` runs `openIsland`'s size and decode check (M4-06) on both copies.
   - If this device's island opens and the file's doesn't, the whole "Use the file's copy" option is removed for that player. The check says so: "…so the file's copy can't replace {name} on this device. You can keep this device's copy, or keep both." (review N3). A forced pick resolves to "kept" (unit tests plus a component test).
   - A file copy with a bad island can still be added as a new player or a copy: nothing good is lost, and M4-07 must not replace a damaged island (decision 99).
   - A device copy with no island at all doesn't block a replace.
4. **The active player is replaced, then an autosave writes the old copy back.** After a successful save, if the id is the active player's, `app.setProfile(fileCopy)` swaps the shell's profile, and Settings' local state follows (`onReplaced`). Unit test "replacing the active player switches the shell to the new copy".
5. **The file is written partly, then something fails.**
   - Each player is its own `store.save` transaction, so a failure affects only that player.
   - A storage error is reported per player ("couldn't be saved. Nothing about that player changed.") and the rest carry on.
6. **Import of a hostile or huge file.**
   - Over 5 MB is refused before it is read: the UI checks `file.size`, and `readExportFile` checks it again (unit test checks `text()` is never called).
   - Bad JSON, the wrong app, a missing version, a newer file or no list: nothing is written, with a reason (component test checks the backing map is unchanged).
7. **Import writes before the grown-up agrees.** Nothing is written until Load players (unit and e2e tests check the store is still empty while the check is shown). "Not now" discards the plan.
8. **The export silently leaves players out.**
   - `exportAll` skips damaged and newer-game records. The screen lists them: "One damaged player was left out…" and "…a newer version of the game saved it. Use the newer game to make a save file with it."
   - A storage failure makes `exportAll` reject. The screen says "We couldn't make the file. Nothing on this device changed." and no partial file is downloaded.
9. **The same id twice in one file (review N1).** Two replacements of one id would put the first file copy into `:prev` over this device's copy, and nothing of the device's would be left. Two guards stop this, and each has a test that fails without it:
   - `planImport`: a repeat of an id is an "add" row, which is always a copy with a new id. It is never offered "Use the file's copy" ("a repeat of a device id … is only a copy, even if both ask to replace"; the component test "the same id twice in the file …" checks that `:prev` still holds the device's copy).
   - `resolveImport`: one id is written at most once per import; a second replace resolves to "not loaded" ("resolveImport refuses a second replace of one id on its own, too").
   - Removing each guard was checked by hand: without the first, 2 tests fail; without the second, 1 fails; without both, 3 fail.
10. **Two tabs open.** Not new to this card. If another tab holds the replaced player in memory and autosaves later, it writes over the imported copy, and the imported copy then sits in `:prev`. This is the same as any two-tab edit today. Noted, not fixed here.

## Decisions

- **The check comes before any write, and the default keeps this device's copy.** "Never silently overwrite; ask, and say which one wins" is met by asking per conflict, stating the result in words, and choosing the non-destructive option by default.
- **Import doesn't call `store.importAll`.** Its rule is "a clash always becomes a copy", and there is no way to ask. The UI uses `readExportFile` plus `store.save` per player. `importAll` stays as the contract's one-shot import, on the same file rules.
- **"Which copy is newer"** compares last played: the latest of `createdAt`, `history[].at` and `lessons[].lastPlayed`. It's a hint; the grown-up still decides.
- **Left out on export** is computed after `exportAll`, as the damaged and read-only ids missing from the file. Damaged records have no readable name, so the screen gives counts.
- **The splash gets a grown-up link** (beside Privacy), and Settings with no player offers a gated import only (there's nothing to export). Otherwise a new device couldn't import without first making a throwaway player.
- **Error copy:** whole-file problems and per-player reasons are `t()` strings for grown-ups. The English `detail` from the validator goes only to logs.
