## Decisions

- **Counting rules are unchanged from M1-03's interim accumulator**, so the six `tests/fixtures/logs/` summaries and the session "summary" tests needed no edit. Per key, a `repeat` wrong key at a `stay` position is not counted again, and a fact with `expected: null` has no key.
- **`summarize(totals, context)` instead of the card's `summarize(acc, activeMs)`.** A summary also needs `config`, `startedAtT` and `uncorrected`, and only the session knows them, so it takes the `SummaryContext` that M1-03 defined (which carries `activeMs`). The accumulator exposes `totals` for it.
- **`recentErrRate` folding.** A summary has counts but not the order of the attempts, so each of the `a` EMA steps (α = 0.1) uses the session's rate `r = errors / attempts`: `next = r + (prev − r) × 0.9^a`. That is the average result over every order of the attempts. A key's first session sets it to `r`.
- **New keys** start with `srs = { intervalSessions: 1, dueSession: sessionIndex + 1 }`. The fold never changes an existing key's `srs`. See Questions.
- **Keys absent from the session** are copied unchanged. A `KeyAgg` with 0 attempts is skipped.
- **`median` of an even count** averages the two middle values (this applies to the baseline and to `latencyMedian`).
- **Stars: an unfinished lesson gets 0 stars**, even when the accuracy would earn more. The second and third stars only add on top of completion.
- **Stars: speed check has a 1e-9 WPM slack.** `20 × 1.1` is `22.000000000000004`, which would deny the star to a kid at exactly 22 WPM. Accuracy needs no slack, because `correct / keystrokes` rounds to the same double as the literal (57/60 === 0.95).
- **Baseline**: filter `history` to mine/practice/minecart, take the newest 10 of those, and return their median, or `null` under 3. `computeStars` takes the baseline as a number or `null`, so the caller computes it from the history _before_ this play.
- **`consistency` with mean latency 0** (every sample 0) is 1, as in M1-03.

## Contract change request / Questions

- **SRS rescheduling: who calls `scheduleSrs`?** §3.6's fold doesn't mention `srs`, and §4's `scheduleSrs(stat, sessionIndex, sessionAccuracyForKey)` (M1-05, still a stub) needs the per-key session accuracy, which the fold has. For now the fold leaves `srs` alone, and new keys get interval 1, due next session. Options: (a) once M1-05 lands, the fold calls `scheduleSrs` with `1 − errors / attempts` for each practiced key, or (b) the caller (M1-07) runs `scheduleSrs` after folding. I'd pick (a): one pure step, and nobody forgets it. It is a small follow-up to `stats.ts`.
- **Stars add up literally**, as §6 is written. With a lesson accuracy goal above 0.95 (for example 0.97), accuracy 0.96 earns the third star but not the second, giving 1 + 0 + 1 = 2. That matches the formula, and the test pins it ("stars add up as written"). If the third star should require the second, the change is one line. No shipped lesson has a goal that high yet.
